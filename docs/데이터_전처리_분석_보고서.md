## 2. 데이터 정제 및 가공 방법

### 2-1. 읽기 규약 — 단일 진입점

모든 원본 읽기는 `common/loader.py:load()` 하나만 쓴다. 개별 `pd.read_csv` 직접 호출은 금지다.

```python
pd.read_csv(path, encoding="cp949", dtype=KEY_DTYPES)
```

세 가지를 강제한다: ① **cp949 인코딩** (공공데이터 포털 원본), ② **코드 컬럼 str 고정**,
③ 파일명 2형식 허용(`서울시_상권분석서비스_{name}_.csv` / `서울시 상권분석서비스({name}).csv`).
인코딩·dtype 누락은 조인 실패의 최대 원인이며, 분산돼 있으면 한 곳만 고쳐도 다른 곳이 남는다.

산출 파일은 전부 **utf-8-sig** (Excel 한글 깨짐 방지).

### 2-2. 결합 순서와 조인 전략 (`build_master.py`)

```
① 인구 3종 분기 슬라이스   21분기 → QUARTERS 5개
② 점포 × 매출   inner   on=[분기, 상권, 업종]      → 업종 62종으로 수렴
③ + 상주인구    left    on=[분기, 상권]
④ + 직장인구    left    on=[분기, 상권]
⑤ + 유동인구    left    on=[분기, 상권]
⑥ + 영역-상권   left    on=[상권]                  ← 단일 키
⑦ 인구 3종 중 하나라도 결측인 행 제거
```

각 선택의 근거:

- **② inner인 이유**: 매출 데이터가 없는 업종은 공급갭을 계산할 수 없다. 62종으로 좁아지는 것은 사고가 아니라 **의도된 동작**이다.
- **③~⑤ left + ⑦ 사후 제거**: 조인 단계에서 잘라내면 몇 개가 왜 빠졌는지 셀 수 없다. 붙인 뒤 세고 제거한다(실측 미매칭 약 0.4%).
- **⑥ 단일 키**: 영역-상권에는 분기 컬럼이 없다. 3키 조인 시 전량 실패.
- **⑦ 유효수요 3요소 중 하나라도 없으면 지표를 만들 수 없다** → 행 유지가 오히려 위험.

**master.csv는 62종을 그대로 유지한다.** 11종 필터는 저장이 아니라 **소비 단계**에서 건다.
① 11종 폐업률이 타당한지는 62종 대조군이 있어야 판정되고, ② "왜 62종 중 11종인가"가
발표 근거이며, ③ 잘라두면 되돌리려 raw부터 재실행해야 하기 때문이다.

### 2-3. 복제 데이터 취급 — 가장 흔한 사고 지점

상권 단위 컬럼(`총_상주인구_수`·`총_가구_수`·`총_유동인구_수`·`총_직장_인구_수`)은
master에서 **업종 수만큼 복제되어 있다.** 한 상권에 62행이 있으면 인구도 62번 반복된다.

| 금지 | 허용 |
|---|---|
| 상권 단위 컬럼 `sum()` | `mean()` · `median()` · `first()` |
| 복제 상태에서 분위수 계산 | `drop_duplicates("상권_코드")` **후** 계산 |

`build_scores.py:57`이 유형 분류·유효수요 계산 전에 `drop_duplicates("상권_코드")`로
1,545행까지 줄이는 것이 이 규약의 실행이다. 복제 상태로 사분위수를 뽑으면 점포가
많은 업종이 있는 상권이 그 수만큼 중복 투표한 셈이 되어 임계값이 왜곡된다.

### 2-4. 분모 0 · 결측 방어

파생 지표 3종(`유입강도`·`가구당인구`·`청년비율`)이 전부 나눗셈이다.

```python
def safe_ratio(numer, denom):
    return numer / denom.replace(0, pd.NA)      # loader.py:49
```

0을 NaN으로 바꾼 뒤 `dropna()`한다. 막지 않으면 `inf`가 생기고 **분위수 계산이 조용히
왜곡된다** — 예외가 나지 않아 알아채기 어렵다.
공급갭·행정동_폐업률 조인 후에도 각각 `dropna`로 미매칭 행을 제거한다(`build_scores.py:85,93`).

### 2-5. 정규화 — log1p + min-max

| 대상 | 방식 | 근거 |
|---|---|---|
| 인구 3종 | **log1p → min-max** | 직장인구 404배 스케일 차 (§1-5) |
| 공급갭 → 갭점수 | 유형별 min-max | 유형 간 갭 스케일 차 보정 (§5-3) |
| 행정동_폐업률 → 안정성점수 | `1 −` min-max | 방향 반전 |

가중합은 **가중치 합으로 나눈다**. 나누지 않으면 유효수요가 0~3 범위가 되어 공급밀도의
절대 크기가 달라지고, 산점도 x축 눈금이 문서와 어긋난다.

분위수 정규화나 상위 클립은 **의도적으로 채택하지 않았다** — min-max는 단조변환이라
안정성 단독 순위가 바뀌지 않고(영향은 가중합에만), 사용자가 슬라이더로 안정성 비중을
올리는 경로가 이미 있다. *덜 예민한 것이지 틀린 것은 아니다*로 한계 명시.

### 2-6. 정제 결과 검증 — 4개 게이트

"됐어요"가 아니라 **스크립트 출력이 완료 판정**이다. 실행 결과(2026-08-21):

```
check_master  OK: 106,337행 · 상권 1558 · 업종 62 · 행정동 396 · 분기 5
check_scores  OK: 3,443행(후보) · 유형 7종 · 업종 11종 · 상권 1339 · 유효수요 중앙 0.675
check_app     OK: 계약 준수 · 가중치 재계산 일치
check_news    미산출: data/news.csv 없음            ← ❌ (§5-1)
```

게이트가 잡는 것: 유일 키 중복, 행 수 하한, 업종 수 **정확값**(`!= 11`), 유형 집합,
수치 컬럼 범위, 공급갭 전 행 > 0, 안정성점수↔폐업률 상관 부호.

> **업종 수를 상한(`> 11`)이 아니라 정확값으로 검사한다.** 화이트리스트 누락은 초과가
> 아니라 **미달**로 나타나기 때문이다. 실제로 정본에서 커피-음료가 빠져 10종이 산출됐는데
> 상한 검사가 green을 띄운 적이 있다(후보 527건 소실). 정본이 틀렸는데 검사가 못 잡는
> 조합이 이 프로젝트에서 가장 비싼 실패 유형이다.

## 3. 분석 목적 및 접근 방식

### 3-1. 문제 정의

> **"서울 어느 상권에서 어느 외식 업종을 열면 검토할 가치가 있는가."**

산출 단위는 상권도 업종도 아닌 **상권 × 업종 조합**이다. "성수동이 좋다"가 아니라
"성수동 × 커피-음료"가 답의 단위여야 창업 의사결정에 쓰인다.

두 축으로만 판정한다.

| 축 | 질문 | 지표 |
|---|---|---|
| **공급 부족** | 수요 대비 점포가 덜 들어와 있는가 | 공급갭 |
| **안정성** | 이 동네에서 외식업이 버티는가 | 행정동 폐업률 |

화면 문구는 "추천"이 아니라 **"검토 후보"**로 통일한다 — 데이터가 답할 수 있는 범위를 넘지 않기 위해서다.

### 3-2. 핵심 설계 판단 — 비교군을 먼저 정의한다

**서울 전체를 한 줄로 세우면 "번화가가 좋다"는 자명한 결론으로 수렴한다.**
유동인구가 많은 곳이 매출도 많으니 순위 상위가 전부 강남·홍대·명동이 되고, 이건 데이터
없이도 아는 사실이다.

그래서 **① 상권을 유형으로 나누고 → ② 같은 유형·같은 업종 안에서 중앙값 대비 갭을 잰다.**
"발달상권 중에서 커피가 덜 들어온 곳", "가족 주거형 중에서 분식이 비어 있는 곳"이 답이 된다.

절대 규모 대신 **동일 조건 내 상대 위치**를 재는 것 — 이것이 이 프로젝트의 방법론적 핵심이다.

### 3-3. 파이프라인 6단계 (적용 순서가 계약)

```
5-1 업종 한정(11종)  →  5-2 유형 분류(7종)  →  5-3 유효수요·공급밀도
                     →  5-4 공급갭(>0 필터)  →  5-5 안정성  →  5-6 종합점수
```

#### ① 업종 한정 — 외식·식음료 11종

한식 / 중식 / 일식 / 양식 / 분식 / 패스트푸드 / 치킨 / 호프-간이주점 / 제과점 / **커피-음료** / 반찬가게

62종 전체를 다루면 "학원과 치킨집을 같은 자로 잰다"는 문제가 생긴다.
11종 모두 외식·식음료 계열이라 **연령 프로파일 상호 유사도가 0.958**(62종 평균 0.815)로
비교 가능한 집단이며, 이 유사도가 높다는 사실이 역으로 "수요적합도" 지표를 제외한 근거가 됐다
— 업종 간 변별력이 거의 없었다.

화이트리스트는 후보 산출뿐 아니라 **폐업률 집계·추이·노트북 그래프에도 동일하게 적용**한다.
적용처를 전수로 적어두지 않으면 빠뜨린 곳이 조용히 62종으로 남는다.

#### ② 유형 분류 — 규칙 기반 7종

**선처리 3종** (상권_구분으로 즉시 확정): 발달상권형 · 전통시장형 · 관광특구형
**규칙 분류 4종** (골목상권 1,025개에만 적용):

| 순서 | 유형 | 판정 조건 |
|---|---|---|
| ① | 유입 집중형 | 유입강도 상위 25% |
| ② | 청년 밀집형 | 유입강도 25~75% AND 청년비율 상위 25% |
| ③ | 가족 주거형 | 유입강도 하위 50% AND 가구당인구 상위 50% |
| ④ | 일반 주거·생활형 | 그 외 |

**실측 재계산 (20261 · 상권 1,545)**

| 유형 | 상권 수 | 유입강도 중앙 | 가구당인구 | 청년비율 |
|---|---|---|---|---|
| 가족 주거형 | 325 | 194 | **2.06** | 0.27 |
| 일반 주거·생활형 | 319 | 307 | 1.80 | 0.30 |
| 전통시장형 | 270 | 538 | 1.63 | 0.26 |
| 유입 집중형 | 257 | **585** | 1.71 | 0.30 |
| 발달상권형 | 244 | 546 | 1.53 | 0.39 |
| 청년 밀집형 | 124 | 307 | 1.53 | **0.45** |
| 관광특구형 | 6 | 2,105 | 1.46 | 0.33 |

- **임계값은 하드코딩이 아니라 골목상권 분포의 사분위수다.** 데이터가 갱신되면 경계도 따라 움직인다.
- **ML 군집 대신 규칙을 쓴 이유**: 재현 가능하고 설명 가능하다. "왜 이 상권이 청년 밀집형인가"에 조건식으로 답할 수 있어야 발표가 성립한다.
- ⚠️ 상주인구가 극소인 상권에서 유입강도가 폭발한다(실측 최대 **63,943** — 상주 1명 상권 존재). 사분위 기반이라 순위는 안전하나 화면 표시 시 상한 처리가 필요하다.

#### ③ 유효수요 — 인구 3종 로그 정규화 가중합 (1:1:1)

```
유효수요 = [ minmax(log1p(상주)) + minmax(log1p(직장)) + minmax(log1p(유동)) ] / 3
공급밀도 = 전체_점포_수 / 유효수요
```

- **왜 상주인구 단독이 아닌가**: 상주인구를 분모로 쓰면 명동·강남역 같은 유입형 상권의 공급밀도가 폭증해 "전부 공급 과잉"으로 판정된다(실측: 상주 3명 · 유동 5.6만 상권 존재).
- **왜 직장인구를 넣는가**: 상주↔유동은 상관 0.72로 크게 겹치는 반면, 직장인구는 상주와 0.23 · 유동과 0.39로 **독립적인 수요 정보**를 담는다.
- **왜 1:1:1인가**: 후보 3안(1:1:1 / 2:1:1 / 1:1:0.5)의 상위 상권이 거의 동일했다. **차이가 없으면 근거를 못 대는 숫자를 만들지 않는다.**

#### ④ 공급갭 — 후보의 정의

```
공급갭 = (동일유형×업종 중앙 공급밀도 − 해당 상권 공급밀도) / 동일유형×업종 중앙 공급밀도
```

값이 **클수록 점포가 적다** = 진입 여지가 크다.
실측 대조(상·하위 200행): 공급갭 큼 → 평균 공급밀도 7.38 · 점포 4.6개 / 공급갭 작음 → 15.80 · 11.0개.

**`scores.csv`는 공급갭 > 0 인 행만 담는다.** `후보_인정` 같은 플래그 컬럼을 두지 않고
파일 자체를 후보 목록으로 만들었다. 필터 없이 점수만으로 뽑으면 **상위 100개 중 43개가
공급 과잉 조합**(최소 −2.91)이 되어 프로젝트 목적과 정면으로 어긋난다.
공급갭 > 0은 조건이 아니라 **"무엇을 찾는가"의 정의**다.

#### ⑤ 안정성 — 행정동 × 외식 11종 × 4분기

```python
m11 = master[업종 ∈ 화이트리스트 11종]
q4  = m11[분기 ∈ 20252, 20253, 20254, 20261]
행정동_폐업률 = q4.groupby("행정동_코드")[폐업_점포_수].sum()
              / q4.groupby("행정동_코드")[전체_점포_수].sum() × 100
안정성점수    = 1 − minmax(행정동_폐업률)
```

**집계 단위를 두 번 바꿨고, 두 번 다 근거가 있다.**

| 집계 기준 | 단위 수 | 폐업률 표준편차 | 0값 비율 | 판정 |
|---|---|---|---|---|
| 상권 × 업종 | 14,059 | 3.19 | 38% | 기각 — 분산의 84%가 노이즈 |
| 상권 | 1,560 | 1.65 | 11.4% | 기각 |
| 행정동 × 전 업종 | 396 | 0.76 | 1.0% | 대조군 |
| **행정동 × 외식 11종** | **389** | **1.375** | **1.5%** | ✅ **채택** |
| 자치구 | 25 | 0.35 | 0.0% | 기각 — 변별력 소실 |

- **행정동으로 올린 이유**: 상권×업종 폐업률은 표본이 작아 우연이 순위가 된다.
- **11종으로 좁힌 이유**: 전 업종 집계는 학원·부동산중개·미용실 폐업까지 분모·분자에 넣는다. *"왜 학원 폐업률이 제 치킨집 입지 판단에 들어가나요"* 에 답이 없었다. **질문과 지표를 일치시킨다.**
- **되돌림 기준을 측정 전에 고정했다** — 0값 비율 10% 초과 시 전 업종 환원. 실측 1.5%로 크게 밑돌아 확정. *결과를 보고 기준을 만들면 판정이 아니라 사후 정당화다.*

#### ⑥ 종합점수

```
종합점수 = 0.6 × 갭점수 + 0.4 × 안정성점수      (앱 슬라이더로 조절)
```

**가중치를 코드에 고정하지 않고 슬라이더로 위임한다.** 팀이 임의로 정하면
"왜 그 숫자인가"에 답이 없기 때문이다. 기본값 0.6:0.4의 근거는 **변별력 격차**다 —
안정성점수 대 갭점수 표준편차 비가 **2.7배**(0.087 vs 0.237). 변별력이 낮은 지표에
절반의 무게를 주면 사실상 동점 처리기가 된다.

`app/logic.py:rescore()`는 **재정규화하지 않는다.** 필터 후 min-max를 다시 걸면
조건을 좁혔을 때 순위가 뒤집혀 설명할 수 없는 화면이 된다.
그리고 기본 가중치 재계산 결과가 `scores.csv`의 종합점수와 일치하는지를
`check_app`이 검사한다 — **배치 스크립트와 앱이 같은 공식을 쓴다는 기계적 증명**이다.

**앱 3모드**: 📍 입지 탐색(업종 → 상권 Top N) / ☕ 업종 후보 확인(상권 → 공급 부족 업종 Top 5) /
📊 종합 분석(필터 + 슬라이더 → 목록·산점도·상세 패널 **동시 갱신**).
탐색 모드는 사이드바를 아예 그리지 않는다 — 화면 내 선택과 사이드바 조건이 모순되는 구간을 없애기 위해서다.

## 4. 이 프로젝트의 데이터 처리 원칙 (재사용 가능한 교훈)

1. **원본 읽기는 단일 진입점으로.** 인코딩·dtype 누락은 조인을 조용히 깨뜨린다.
2. **조인은 코드로만, 명칭은 표시용.** 한글 명칭 매칭은 공백 하나에 실패한다.
3. **0은 결측이 아니다.** 새 컬럼을 지표에 쓰기 전 `describe()` 1회 — `아파트_가구_수`가 이 규약을 만들었다.
4. **복제된 상권 단위 값을 합산하지 말 것.** 분위수는 `drop_duplicates` 후.
5. **파일은 넓게, 필터는 소비 단계에서.** 자르면 되돌릴 수 없고 대조군이 사라진다.
6. **판정 기준은 측정 전에 고정한다.** 결과를 보고 기준을 만들면 사후 정당화다.
7. **차이가 없으면 근거 없는 숫자를 만들지 않는다.** (인구 가중치 1:1:1)
8. **검증은 상한이 아니라 정확값으로.** 계약 위반을 못 잡는 검사는 없느니만 못하다.
9. **완료 = 게이트 출력.** 산문 보고는 완료가 아니다.
10. **게이트가 검사하지 않는 것을 명시한다.** 형식은 기계가, 유용성은 사람이 본다.

### 5-2. ❌ 아티팩트 5 미산출 — `industry_trend.csv`

### 5-3. ⚠️ 갭점수 정규화 — 코드가 앞서고 문서가 뒤처졌다

DEV_SPEC §5-6은 "각 지표를 minmax로 정규화"라고만 적고 있으나,
`build_scores.py:100`은 **유형별** min-max다.

```python
s["갭점수"] = s.groupby("유형")["공급갭"].transform(minmax).round(4)
```

커밋 `fff1128` *"발달 상권 데이터 완화를 위한 갭점수 정규화(minmax) 진행"* 에서 의도적으로
바꾼 것으로 확인된다. 실측상 **7개 유형 각각의 최대 갭점수가 모두 1.0**이며,
전체 상관(공급갭↔갭점수)은 1.000이 아니라 **0.9895**다.

- 효과: 유형별 갭 스케일 차(발달상권형 최대 0.927 vs 관광특구형 0.676)를 보정 → 유형 간 후보가 고르게 섞인다.
- **조치 필요**: ① DEV_SPEC §5-6 문구 갱신, ② `notebooks/analysis.ipynb` 그래프 05 해설의 *"갭점수 = minmax(공급갭) · 상관 1.000"* 문장 정정.

### 5-4. ⚠️ 실측 수치가 갱신되어야 하는 항목

| DEV_SPEC 기재 | 재계산 값 (20261) |
|---|---|

| 골목상권 1,026개 | **1,025개** |

### 5-5. ⚠️ `app/logic.py` 코드 위생 2건

- **`load_master`가 두 번 정의된다** (64행 / 77행). 뒤 정의가 앞을 덮어쓰며, 뒤쪽이 `FileNotFoundError` 폴백을 가진 버전이라 **동작상 문제는 없다.** 앞 정의를 삭제하면 된다.
